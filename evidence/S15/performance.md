# Скорость и нагрузка S15

19.10.2026 Москва. Apple M2, 8 логических CPU, 16 GiB, macOS 26.6.2 ARM64, Python 3.13.11, SQLite 3.50.4 DELETE/FULL, Flask 3.1.3, Werkzeug 3.1.9, Waitress 3.0.2 (4 потока), локальный диск. Сервер/worker/клиенты на одном ноутбуке, машина не резервировалась эксклюзивно; это не чистый лабораторный стенд. Показатели — наблюдения, не обещание задержки.

Команда `.venv/bin/python evidence/S15/measure.py` → exit0; raw запросы/ресурсы/версии/журналы — load.json, одиночные операции — performance.json. Каждый режим начинает новую временную синтетическую базу с 6 seed-профилями и 5/25/50 связанными парами; роли 50/50. Барьер одновременного старта, 4 цикла по 5 запросов на пользователя без пауз. GET кабинета/карточки/истории, поиск и проекты решений врача, POST самоотчёта пациента. Два из четырёх самоотчётов каждой пары критические по существующему синтетическому правилу. Отдельные HTTP-клиенты врача опрашивают API раз в3с и посылают квитанцию; после нагрузки финальный drain. Максимальное реальное число TCP-соединений не измерялось: число пользователей — виртуальные сессии, а не измеренная одновременность соединений. ## Вход и границы метода

Первый прогон: 10 HTTP-входов и нагрузка прошли; в подготовке 50 сессий 11-й вход с127.0.0.1 вернул429. Это действующий лимит10попыток/15мин на адрес, включая удачные; исходный отказ сохранён в measure-initial.log/load-initial.json. В окончательной нагрузке сессии заранее созданы штатной authenticate с отдельным вымышленным адресом192.0.2.x для каждого клиента; серверный код/защита не менялись. Стоимость этой подготовки сохранена отдельно (включает текущий scrypt), но это не HTTP-вход и не замер конкурентной аутентификации. Массовый вход за одним NAT остаётся эксплуатационным ограничением B16; лимит не ослабляли. Промежуточный удачный прогон без параллельного polling сохранён в load-without-polling.json/performance-first.json; актуальны load.json/performance.json и measure-final.log.

## Узкие места и пределы

SQLite допускает одного писателя; даже чтение HTTP обновляет last_seen сессии под BEGIN IMMEDIATE. Worker конкурирует за тот же write-lock. Четыре потока Waitress/очередь и частый polling увеличивают задержку. Длинная история/проекты увеличивают генерацию HTML; в полном прогоне для такой карточки p95 около0,75с на странице решений. Эти причинные направления видны по коду и результатам, но точная доля каждого фактора не установлена профилированием. Первое улучшение при отдельном поручении — ограниченные выборки/страницы истории и измерение обновления сессий; изменения клинических правил не нужны.

100 сессий проверены лишь коротким всплеском около7с с50карточками. Продолжительная нагрузка, большие истории на всех карточках, конкурентный scrypt, длительный рост очереди, внешняя сеть/TLS/мобильные устройства/несколько хостов не измерены. Увеличение числа worker/потоков само по себе не снимает ограничение SQLite. Горизонтальное масштабирование потребует отдельного решения по БД/очереди/хранилищу и новых проверок. B12 не воспроизведён здесь, причина прежних404/409 не установлена и риск не закрыт.
