# Синтетические случаи S03

Версия S03-v1, 18.10.2026, Москва. Набор составлен Codex с нуля по типам проверок из карточки S03 и неактивного каталога S02. Реальные истории болезни, имена, контакты, идентификаторы людей и ответы пациентов не использованы. Каждый объект содержит происхождение и `synthetic=true`. Это собственные технические примеры проекта; разрешение считать синтетику конкурсной апробацией не получено (B07/Q07/Q12).

## Состав

| Файл | Содержание | Назначение |
|---|---|---|
| `data/synthetic/cases.json` | 6 отдельных профилей D01–D06 | Основа сквозной демонстрации S07–S11/S18 |
| `data/synthetic/extraction-development.json` | 24 истории DEV01–DEV24 | Разработка извлечения в S12 |
| `data/synthetic/extraction-holdout.json` | 12 историй H01–H12 | Отложенная техническая проверка в S12 |
| `data/synthetic/manifest.json` | Версия, количества, SHA-256 трёх файлов | Зафиксировать набор до реализации извлечения |

Всего 42 отдельных вымышленных профиля, из них 36 текстовых историй и 210 размеченных утверждений. Рабочая цель 30–60 историй соблюдена без подсчёта демонстрационных случаев как дополнительных историй. Используется 12 вариантов подачи: хронологическая запись, разделы, диалог, краткая запись, рассказ, последовательность событий, назначение в начале, самоотчёт, смешанные источники, список, архив и цитата. Это разнообразие способов записи, не 36 разных поддерживаемых файловых форматов. На этом этапе есть только текст внутри JSON, не DOCX/PDF/OCR и не реализованный импорт.

## Шесть демонстраций

В каждом случае есть профиль, отдельное рассмотрение Авиандра, проект лечебной рекомендации и проект маршрутизации. Установленные внутри вымысла диагнозы не являются реальными врачебными подтверждениями.

| ID | Содержание | Что нужно показать в будущем приложении |
|---|---|---|
| D01 | ГТР, кандидат рассмотрения | Справка по препарату после всех проверок; возможность обсуждения не равна назначению |
| D02 | Ровно 18 лет, беременность, неизвестные ограничения | Не переносить общую взрослую применимость на точные границы препарата; уточнить ограничения |
| D03 | Депрессивные жалобы без установленного показания | Не выводить показание из симптомов; подготовить оценку и профильную консультацию |
| D04 | Ухудшение и сообщение о намерении причинить себе вред | Отделить новое сообщение от обычного рассмотрения терапии; проверить кандидат обязательного маршрута |
| D05 | Жалоба и пропуск приёма | Разделить сообщение, причинность, пропуск и врачебное изменение плана |
| D06 | Противоречивые возраст/режим, неполная анкета | Не выбирать значение молча, не суммировать неполную форму; показывать недостающие основания |

Лечебные тексты — содержательные проекты для последующей проверки, без подтверждённой дозировки или активного назначения. В маршрутах `category=null` и `urgency=null`: предполагаемую обязательность D04 должен независимо проверить врач/эксперт по научному основанию. Остальные случаи тоже содержат вопрос о маршруте и ограничение его утверждения. Полные сценарии продукта и M04 ещё требуют реализации и проверки. Все проекты `active=false`, `clinical_review_status=not_reviewed`, `clinical_expectation=null`; B04 сохранён, B03 дополнительно указан для случаев со шкалами. Утверждение клинической пригодности E02 требует фактического отчёта врача в S16.

## Разметка текстов

`id` обозначает запись, `profile_id` — отдельного вымышленного человека. Один профиль встречается только в одной части; демонстрационные профили также отдельные. `text` — исходный текст, без автоматического дописывания отсутствующего. Каждый элемент `facts` содержит поле, состояние утверждения, значение, точную цитату и границы цитаты. Смещения считаются по Unicode-символам Python: начало с нуля, конец не включён. Для JavaScript нельзя молча использовать эти числа как позиции UTF-16 при появлении символов вне основной плоскости; получать цитаты с учётом соглашения.

`target_fields` заранее фиксирует поля оценки для конкретной истории. Разметка не претендует на описание всех медицинских сведений в тексте. В S12 результаты оцениваются только по этим полям; остальные поля не увеличивают число ошибок и не используются для расширения эталона после просмотра результата. Если нужен другой охват, создать новую версию до запуска проверки. Для повторяющегося целевого поля все размеченные утверждения учитываются отдельно: например, два спорных возраста или две дозы нельзя свернуть в одно значение.

| Состояние | Значение |
|---|---|
| `present` | Утверждение явно присутствует в синтетическом тексте |
| `negated` | Явное отрицание; не отсутствие поля |
| `considered`, `suspected` | Обсуждение препарата или подозрение на диагноз |
| `patient_reported`, `listed` | Самоотчёт либо запись в списке; не доказательство фактического приёма |
| `historical`, `stopped`, `cancelled_proposal` | Прошлое, отменённая терапия либо отвергнутый проект |
| `conflicting` | Сохранить оба несовместимых утверждения без выбора |
| `third_party` | Слова о другом человеке; не собственный риск/препарат пациента |
| `unknown`, `invalid`, `not_due` | Неизвестное, некорректное либо событие ещё не наступило; значение `null` |
| `incomplete` | Частичное значение, например число без единицы; отсутствующая единица `null` |

`medication` — упоминание препарата с его статусом; `medication_name` в пропусках — неизвестное название фактически обсуждаемой/принятой таблетки. Историческое упоминание Авиандра не заполняет это поле автоматически. `diagnosis` описывает запись/подозрение; `confirmed_diagnosis`, `current_diagnosis` и `primary_diagnosis` отмечают отдельно отсутствующее подтверждение, актуальность или ведущий диагноз. Аналогично `confirmed_current_regimen` не выводится из спорного/старого назначения, `current_adherence` не выводится из молчания. Остальные обозначения раскрываются текстом и точными цитатами каждой истории; перед измерением S12 фиксирует единое отображение поддерживаемых полей.

Для даты хранится ISO `YYYY-MM-DD`, если она однозначно выводится из исходного текста. Двузначный год H08 относится к 2026 в заданном контексте синтетического набора; для реального импорта такую договорённость утверждать отдельно. Невозможные даты DEV24/H12 остаются `invalid`, без исправления на соседний день. Дозы сохраняют исходную единицу (`mg`, `g`, `ml`, `tablet`) и десятичное значение; не превращать объём или половину таблетки в мг без концентрации/силы. Все назначения и дозы в текстах — вымышленные входные данные, а не режимы, подтверждённые инструкцией.

`critical_missing_fields` — важные для данной технической проверки поля без сообщённого пригодного значения. Они не имеют вымышленных цитат и не заменяются нулём/`false`. Если явное сообщение об неизвестном включено в `facts`, оно имеет цитату и не дублируется как отсутствующее поле. Неуказанные значения, например версия бланка, могут быть отмечены только в `critical_missing_fields`. Список критичных пропусков составлен для проверки поведения, а не как утверждённый клинический перечень обязательных входов.

## Разделение и предел независимости

Профили и их входные сочетания составлены отдельно; в контрольную часть не перенесены перефразировки разработочных историй. Проверка сравнивает ID профилей, тексты и смысловые наборы размеченных входов/пропусков без возраста, даты и формулировок. Смена возраста или даты сама по себе не делает профиль новым. Дополнительно ищутся похожие тексты между частями; сходство ниже 0,85 — только технический индикатор, не доказательство статистической независимости. Оба набора вручную прочитаны при составлении и приёмке.

Контроль заранее выделен и зафиксирован до реализации извлечения. Разработчик S12 использует только development при настройке, затем один раз запускает зафиксированный holdout. Поскольку автором набора и будущей реализации может быть Codex, это отложенный технический контроль с ограниченной независимостью, **не слепая внешняя клиническая проверка**. Набор доступен в репозитории и технически не скрыт. Если контрольные примеры использовали для настройки или уже просмотрели ошибки и изменили извлечение, следующий результат называется повторной проверкой на известном наборе; для новой независимой оценки нужны новые, заранее зафиксированные профили. Переносить H-профили в development нельзя.

## Проверки сейчас и далее

`python3 tools/validate_synthetic.py` проверяет количества, происхождение, неактивность, SHA-256, профили, целевые поля, цитаты/смещения, состояния, нормализованные даты и разнообразие отрицаний/единиц/назначений. Отдельные отрицательные проверки валидатора — `python3 -m unittest discover -s tools -p 'test_synthetic_validation.py'`. Проверка контактных шаблонов — вспомогательная; отсутствие реальных персональных данных основано также на происхождении и чтении всех текстов, а не на обещании автоматического обезличивания.

В S12 до запуска зафиксировать поддерживаемые поля/форматы, правила сопоставления и подсчёта точности/полноты, версии программы/набора, ошибки, пропуски и отказы. Ожидаемое извлечение здесь следует из конкретного текста; медицинская истинность текста не оценивается. Клинические ожидания отсутствуют и не могут служить единственным эталоном от модели: нужны первоисточники и реальная независимая проверка B04/S16. Сейчас извлечение не реализовано, метрики точности/полноты, доставка уведомлений и клиническая апробация не измерялись.
