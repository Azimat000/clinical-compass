# S16 — как провести проверку с участниками

Статус: инструкция подготовлена; проверка ещё не проведена. Версия протокола S16-v1, 19.10.2026. Проверяем локальный прототип на вымышленных случаях. Это не исследование эффективности лечения и не разрешение применять продукт к реальным пациентам.

## Кто участвует и что записать до начала

Не передавайте проверяющим закрытые материалы кейса и данные организатора. Используйте собственные синтетические задания; при внешних участниках отдельно проверьте допустимость раскрываемых экранов/текстов.

Нужны человек с квалификацией врача для проверки содержания и люди, выполняющие задания двух ролей. Участник в роли пациента не должен быть настоящим пациентом. Небольшая первая проверка может состоять из врача и другого человека; это предложенный начальный состав, не установленный конкурсом минимум и не доказательство достаточности выборки. Можно привлечь больше участников. Если человек состоит в команде/создавал продукт, это записывается: такую проверку нельзя представлять как независимую внешнюю оценку.

В локальном журнале запишите дату, код участника (например V01/U01), роль, медицинскую специальность/способ подтверждения квалификации врача, связь с командой, опыт использования прототипа, согласие участвовать и границы использования замечаний. Не включайте ФИО, контакты, документы о квалификации, диагнозы участников в Git. В отчёт идут только разрешённые обезличенные сведения; код участника сам по себе не гарантирует обезличивания. Отдельно договоритесь о хранении и удалении исходных заметок; фото/видео/звук по умолчанию не нужны. Участник может остановиться и пропустить задание; это записывается без выдуманного результата.

Перед началом прочитайте вслух: «Проверяем программу на вымышленных данных, а не ваши знания и не ваше здоровье. Не вводите сведения о себе или реальных пациентах. Можно остановиться в любой момент. Мы запишем время, действия, затруднения и ваши замечания. Назначения и сообщения внутри демо относятся только к вымышленному случаю».

Ведущий заранее фиксирует версию: `git rev-parse HEAD` и `git status --short`, дату/время, ОС, браузер и его версию. Укажите, используется ли текущий чистый коммит или есть изменения. Медицинские источники врач открывает из реестра `docs/clinical/sources.md`; дату их актуальности на момент проверки фиксируют отдельно. Не заявляйте повторную проверку источников, если её не было.

## Подготовка компьютера

Работайте на одном компьютере с локальным адресом. Врач и участник могут действовать последовательно, выходя из аккаунта, или в отдельных профилях браузера (не в двух вкладках одного профиля: сессия общая). Не публикуйте сервер и не открывайте внешний доступ. Зависимости уже установлены в `.venv`; если окружения нет, сначала следуйте `docs/RUNBOOK.md`.

Создайте НОВУЮ отдельную папку. Команда `mkdir` без `-p` специально откажется использовать существующую. При повторной проверке замените `s16-round1` во всех командах на новое имя. Обычную рабочую базу не используйте.

```sh
umask 077
mkdir -p var
mkdir var/s16-round1
.venv/bin/python -m apps.compass --db var/s16-round1/demo.sqlite3 seed-demo
.venv/bin/python -m apps.compass --db var/s16-round1/demo.sqlite3 seed-accounts > var/s16-round1/credentials.json
.venv/bin/python -m apps.compass --db var/s16-round1/demo.sqlite3 serve --port 18016
```

Если любая команда mkdir завершилась ошибкой, остановитесь и выберите новое имя: последующие команды не запускать. Пароли лежат только в `var/s16-round1/credentials.json`, их не передавать в отчёте. Не повторяйте seed-accounts с перенаправлением в тот же файл: он выдаёт только новые пароли.

В другом терминале из HAC запустите обработку очереди:

```sh
.venv/bin/python -m apps.compass --db var/s16-round1/demo.sqlite3 worker
```

Откройте http://127.0.0.1:18016. Врач входит как `doctor-demo`, роль пациента — `patient-D01` (для других случаев — patient-D02…D06); пароли из файла. Врач создаёт приглашение к нужному случаю, соответствующий пациент принимает его. В новой базе связи изначально нет. Все случаи синтетические. Для каждого D01–D06 связь создаётся отдельно. Не делайте больше 10 входов за 15 минут с одного адреса: лимит включает успешные входы. Распределите раунды по времени, защиту не отключайте.

Для первичного раунда достаточно связать D01, выполнить задания пациента/врача, затем продолжить клиническую сверку остальных случаев с учётом лимита. При проверке в другой день используйте фактическую дату; старые случаи не превращайте молча в текущие факты. Для правил, требующих сегодняшней записи, врач вводит отдельный явно вымышленный текущий контекст. Исходные файлы S03 не переписываются.

Завершение: Ctrl+C в терминалах сервера и worker. Базу/пароли не включать в Git и не отправлять в чат. Срок хранения/удаление локальной папки согласовать с ведущим; не удалять результаты до проверки отчёта.

## Как измерять задания

Перед каждым заданием ведущий подготавливает исходное состояние. Подготовка не входит во время выполнения. Читайте участнику только текст задания, не ожидаемый результат. Запуск секундомера — после прочтения, когда участник начинает; остановка — при наблюдаемом результате либо отказе. Запишите длительность, в том числе неуспешной попытки. Один щелчок/касание, переход клавишей Tab, подтверждение Enter, прокрутка или заполнение одного поля считается одним действием; отдельные буквы не считаются. Считайте одинаково во всех раундах. Время размышления входит, внешние перерывы отмечаются отдельно.

Итог задания: `без_помощи`, `с_помощью`, `не_выполнено`, `пропущено`. Вопросы ведущему и каждую подсказку записывать. Если ведущий показал решение, это не успех без помощи. Незаполненное измерение остаётся пустым, не нулём. Порядок/повторы/обучение и проблемы связи записываются.

После заданий спросите: «Что было непонятно? Где ожидали другой результат? Что могли бы понять ошибочно? Что стоит изменить первым?». Запишите слова участника с его разрешения и код задания. Наблюдение ведущего и мнение участника храните раздельно.

Врач отдельно проверяет каждый D01–D06 по `evidence/S16/clinical-review.md`. Если задание недоступно/возникла ошибка — записать фактический шаг и результат, а не подменять демонстрацией ведущего. Существенное опасное непонимание — повод остановить сценарий и сохранить замечание; исправление проверяется новым раундом с новой версией, старые результаты остаются.

## Что вернуть после проведения

Скопируйте пустые формы `evidence/S16/participants.csv`, `task-results.csv`, `clinical-findings.csv` в закрытую локальную папку `var/s16-round1/`. Заполните только реально проведённое. Времена — секунды, действия — целые числа; незамеренное пусто. Эти файлы в Git являются шаблонами только с заголовками, не записями участников.

Для продолжения достаточно передать в чат обезличенный отчёт: версия/дата/среда, число участников и роли/связь с командой, результаты каждого задания, время/действия/подсказки, замечания врача по каждому случаю и разрешённые выдержки. Проверить возможность идентификации по сочетанию сведений. Пароли/базу/реальные истории/личные документы не передавать. Не нужно загружать видео или раскрывать ФИО.

Успешность без помощи = число выполненных без помощи / число реально начатых заданий; с помощью показывать отдельно. Пропущенные перечисляются отдельно и не попадают в знаменатель, но остаются видны. Время успешных и неуспешных попыток показывается раздельно, при малом числе — индивидуально. Нельзя выводить экономию времени врача без сопоставимого измерения того же задания обычным способом: если сравнение проводится, заранее задать одинаковые по сложности случаи, порядок/обучение/ограничения и сохранить оба результата. Одна оценка «удобно» не измеряет эффективность.

C10/C42: капитан может получить фактическое уточнение у предусмотренного трекера/организатора о формате апробации и допустимых доказательствах. Зафиксировать дату, роль отправителя, канал и разрешённую точную формулировку ответа. Эта инструкция никому не отправлена. Отсутствие такого ответа не объявляется запретом локальной проверки с вымышленными данными; соответствие ожиданиям конкурса пока не подтверждено.
