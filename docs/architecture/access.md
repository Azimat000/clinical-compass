# S05: локальный доступ двух ролей

18.10.2026. Только синтетика. Роль «Врач» общая; специальность не является фильтром допуска. Пациент видит только собственную карточку, врач — только текущую связанную карточку после принятия приглашения.

## Поток

1. CLI seed-accounts создаёт двух врачей и отдельные учётные записи свободных синтетических пациентов; пароли случайные, хэши scrypt:32768:8:1. Существующие учётные записи/связи не перезаписывает. Пароли печатает только один раз в локальный вывод. Автоматического восстановления/HTTP-регистрации нет.
2. GET /login выпускает случайный одноразовый challenge (10 минут), в БД только SHA-256; форма + HttpOnly cookie. POST /login потребляет challenge, резервирует попытку по хэшу ID и адресу в 15-минутном окне, проверяет пароль (также фиктивный хэш неизвестного ID). Роль берётся из БД, входные role/doctor_id не используются.
3. Успешный вход создаёт 256-битный случайный SID и отдельный CSRF; сервер хранит только SHA-256 SID, user_id, CSRF, expires_at и last_seen_at. Старый представленный SID отзывается. Максимум 8 часов, простой 30 минут. Каждый защищённый запрос заново проверяет enabled/роль/срок/отзыв, небезопасный метод — CSRF с постоянным временем сравнения. Logout POST отзывает SID в БД. Старые S04-сессии без CSRF/last_seen_at не принимаются.
4. Врач создаёт приглашение по заранее известному коду пациента. Приглашение содержит хэш случайного 256-битного токена, patient_id, recipient_user_id, doctor_id, created_at/expires_at, consumed_at/revoked_at. Врач видит исходный токен однократно; в URL код не помещается. Карточку/документы создание приглашения не открывает.
5. Пациент принимает код из собственного кабинета: BEGIN IMMEDIATE повторно проверяет получателя, владельца карточки, включённых участников, срок/отзыв/использование и отсутствие текущего врача. Создание связи и потребление токена атомарны; частичный уникальный индекс не допускает двух активных ведущих врачей. Конкурирующие приглашения отзываются. Самостоятельной смены врача нет.
6. Пациент отправляет фиксированный технический отчёт проверки связи без медицинских полей; relationship_checks связывает его с текущей парой и пользователем. Оба кабинета читают одну запись из БД. Это демонстрация маршрута пары для S05, не реализация полного самоотчёта F06/M02/S06. Клинические входные данные фиксированный маршрут не принимает.

## Поверхность HTTP и запреты

| Маршрут | Доступ / поведение |
|---|---|
| /healthz, /static, /login | Без входа; никаких данных пациента |
| / | Врач: только собственные связанные случаи/поиск. Пациент: переход в свою карточку |
| /demo/id, /api/patients/id | Собственный пациент либо текущий ведущий врач; иначе 404 |
| /api/patients/id/documents, /reports | Та же проверка пары перед запросом данных |
| /api/documents/id | Сначала проверка владельца пациента; чужой 404, свой 409: выдача файлов выключена |
| POST /invitations, /invitations/hash/revoke | Только врач; отзыв только своего предложения |
| POST /link | Только получатель с ролью пациента |
| POST /patients/id/connection-check | Только владелец-пациент с действующей связью и включённым врачом |
| POST /api/patients/id/actions | Только свой ведущий врач достигает 409 clinical_actions_inactive; пациент 403, чужой врач 404. Записей действия/подтверждения не создаёт |
| POST /logout | Текущая сессия + CSRF, отзыв на сервере |
| Остальные методы/маршруты | 404/405, операций записи нет |

Окончание связи сразу закрывает врачу карточку и ресурсы даже со старой действующей сессией. Фильтр поиска применяется в SQL к связанным пациентам, а не после выдачи страницы. Пользовательские значения идут в SQL-параметры/Jinja с экранированием. storage_key не интерпретируется как путь для скачивания. CSRF/SID/пароли/исходные токены приглашения не записываются в аудит. Записываются безопасные события входа/выхода/создания/отзыва/принятия/проверки связи; полный журнал отказов/мониторинг ещё S14.

## Пределы

Cookie HttpOnly/SameSite=Strict/Path=/; HTTP на loopback — Secure выключен. COMPASS_COOKIE_SECURE=1 включает Secure/HSTS при отдельно подготовленном HTTPS. Trusted Host, CSP form-action/frame-ancestors, no-store, no-referrer, nosniff; CORS не включён. Нет Flask-клиентской cookie с ролью, секретного ключа для подписания или стороннего авторизационного сервиса.

Случайные пароли и постоянные лимиты достаточны для этого локального синтетического среза; полного подтверждения защищённости/конфиденциальности нет. S14/S15: усиление/замер scrypt относительно OWASP, аудит/резервные копии, управление аккаунтами/паролями/отзывом всех сессий при административной смене прав, TLS/прокси, ресурсные ограничения/мониторинг. База/credentials приватны на машине, не публикуются. CLI-администратор имеет доступ к базе; защита от владельца компьютера не заявлена.
