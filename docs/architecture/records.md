# Карточка и история S06

Локальный синтетический ввод без шкал, лекарственных правил и клинических решений. Пациент после связи с ведущим врачом отправляет самоотчёт; врач добавляет визит. Оба открывают одну карточку из одной базы. Сохранённые данные видны при открытии/обновлении страницы; фоновые уведомления и измерение задержки доставки относятся к S10.

## Поток и хранение

- POST `/patients/<id>/self-reports`: только владелец-пациент с действующей связью и включённым врачом. POST `/patients/<id>/visits`: только текущий связанный врач. Автор берётся из серверной сессии, не из формы.
- GET `/api/patients/<id>/history`: те же проверки видимости, история обеих ролей; внутренний ключ повтора не выдаётся. Существующий `/reports` сохраняет совместимость и выдаёт самоотчёты schema_version=2.
- Миграция 003_records добавляет clinical_entries (тип, patient/actor, дата наблюдения, точное время приёма, резюме, проверенный снимок, ключ повтора и ссылку на encounter/self_report). UPDATE/DELETE clinical_entries запрещены триггерами; исправление — новая запись, старые остаются. Удаления/редактирования через HTTP нет.
- Визит создаёт encounters с author_id/днём наблюдения/ссылкой происхождения и обновляет существующий индекс поиска. Самоотчёт создаёт self_reports с reported_at=календарный день наблюдения, received_at=фактическое UTC-время. Это не точное время возникновения симптома.
- Жалобы, сообщённые факторы риска, сопутствующие препараты и НЯ — четыре observations с собственным статусом/значением/датами/JSON-происхождением. Пятая observation — возраст. Резюме не используется для автоматического извлечения/оценки рисков.
- НЯ со статусом known/conflicting дополнительно создаёт adverse_events с source_entry_id и unreviewed; therapy_id NULL, причинность/связь с препаратом не установлена. unknown/denied остаются отдельными observations без фиктивного события.
- Все вставки и audit создаются в одной BEGIN IMMEDIATE. Проверка доступа повторяется внутри транзакции. Ошибка откатывает весь набор, включая self_report/encounter. Повтор одинакового ключа/содержимого для того же автора/пациента/типа возвращает прежний ID; изменённое содержимое с тем же ключом — 409. Новый ключ создаёт новую запись, даже если текст похож: это намеренно не глобальное удаление похожих наблюдений.

## Неизвестное и противоречия

Пустые поля по умолчанию unknown; значения NULL. denied — явное отрицание, не значение по умолчанию. known/conflicting требуют описание. Текст при unknown/denied отвергается, чтобы не скрывать его за статусом. Неполная запись допустима с явными пропусками. Полнота записи не является подтверждением отсутствия риска.

Возраст относится к дню наблюдения: 0–120 полных лет, дата рождения не позже дня наблюдения, будущие дни не принимаются. Можно сообщить возраст или дату рождения, либо оба. Несовпадение двух величин сохраняется как conflicting с обоими исходными значениями. Неизвестный возраст не получает число/взрослый допуск. Исходный профиль S03 остаётся отдельно с источником; новые сообщения его не перезаписывают. Приложение S06 вообще не принимает автоматическое решение о возрастной применимости инструмента.

На один день разные known/denied или разные тексты/значения подсвечиваются как расхождение источников, требующее сверки. Это сравнение данных, не медицинское заключение: разные формулировки могут быть совместимы, разные дни могут отражать изменение. Противоречие, явно указанное автором, тоже видно. Исправляющие новые записи не «разрешают» старые расхождения автоматически: процедура клинического согласования ещё не реализована.

## Границы проверки

Таблица динамики показывает дату/источник/субъективное «лучше/без изменений/хуже/не указано»/возрастной статус и ссылки на полные записи. Баллов, оценки тяжести, сопоставления шкал или графика клинического эффекта нет — S07. Все ограничения типов/дат/длин/согласованности выполняются на сервере. Ошибка 400 сохраняет введённый текст в форме с экранированием; SQL параметризован, Jinja экранирует вывод, CSP прежняя. Audit содержит ID/автора/событие, а не тексты жалоб или пароли.

Проверки: apps/tests/test_records.py, расширенный smoke_restart.py на настоящем HTTP/Waitress; свидетельства/матрица — evidence/S06. Полный правовой/безопасностный аудит, нагрузка, жизненный цикл аккаунтов и резервное восстановление остаются S14/S15/S17. Синтетические проверки не являются клинической апробацией.

## S42 — разделение дневника и истории приёмов, 25.10.2026

Самочувствие в карточке, дневнике и сводке содержит только `kind=self_report`. Короткие врачебные записи `kind=visit` показываются в истории приёмов; их исходные `clinical_entries` и связанные `encounters` не меняются. `records.legacy_encounters` выбирает только самостоятельные архивные encounters без ссылки из clinical_entries, поэтому врачебная запись не дублируется. Подробные приёмы и версии `first_visit_versions` остаются в своём хранилище; список показывает последнюю версию, история всех версий сохранена.

POST self-reports создаёт самоотчёт пациента и ведёт в дневник; исторический POST visits создаёт запись врача/encounter и ведёт в first-visits#entry-ID. Неизвестный тип `records.save` отвергается до вставок. Неверная врачебная отправка получает видимую ошибку; не возвращается в невидимую пациентскую форму. Роль определяется сервером, повторы по прежнему ключу не создают дублей. API history по-прежнему возвращает оба явно обозначенных типа для совместимости и проверки исходных фактов. Сверка противоречий, возрастные основания и нежелательные явления продолжают учитывать все исходные записи.

GET `/patients/<id>/records/<entry_id>` проверяет доступ к пациенту и принадлежность записи, затем ведёт к нужному разделу по типу и роли. Переписка использует этот переход и явно называет запись самочувствия либо приёма. Прежние врачебные #entry-ID на карточке сохранены в отдельном разделе истории. Пациент читает прежде доступные ему короткие врачебные записи отдельно на `/demo/<id>/visits`; подробные врачебные приёмы/черновики этой странице не передаются и по прежнему недоступны пациенту.

Изменение представления без миграции/переписывания исторических данных; технические проверки — evidence/S42 и apps/tests/test_record_routing.py.
