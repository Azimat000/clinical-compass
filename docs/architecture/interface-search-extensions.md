# S13: рабочие экраны, поиск и расширения

## Интерфейс

Flask/Jinja + CSS/обычный JS, без новых пакетов/шрифтов/сервисов. Направление ниже историческое: интерфейс и локальные навыки удалены по прямому поручению 22.10.2026; фактическое решение и исходные/итоговые экраны — evidence/S13/design-contract.md и platforms.md.

Общий header/sidebar/footer задаёт base.html. Список врача — строки, поиск/фильтры первыми, приглашение в details. Карточка показывает обзор, запись, историю/динамику, анкеты, сверку/источники. Это обычные ссылки с якорями; interface.js скрывает невыбранные группы и обновляет aria-current, открывает старые якоря/ошибки, поддерживает «назад». Без JS все разделы остаются доступны. Ошибки самоотчёта сохраняют введённые значения/ключ повтора; понятные ошибки возле несогласованных полей связаны aria-describedby, фокус у общего сообщения. S27 добавляет личный серверный черновик самоотчёта: после подтверждённого сохранения поля восстанавливаются при открытии; неподтверждённые правки могут потеряться. Подробности — report-drafts.md. localStorage и внешних хранилищ нет.

Сохранённая запись, проект, подтверждённое решение, квитанция отображения, просмотр, принятие и фактическая реакция не объединяются. Обязательно — слово/⚠/сплошная рамка; желательно — слово/◇/штриховая рамка. Критический баннер врача вне переключаемых разделов; на узком экране не закрепляется поверх формы. Неполные/противоречивые сведения видны отдельно. Формы решения показывают относящиеся к выбранному типу поля; скрытие не меняет серверные проверки. Пациент не получает проекты/врачебные снимки/баллы. Точные медицинские тексты и формы не менялись.

## Поиск и новая схема

012_search.sql — только добавление. Не исправлять принятые SQL 001–011 и schema_migrations вручную. На прежней базе штатно запустить текущий сервер/миграцию; FTS заполняется из прежних записей. Все прежние строки/версии/решения сохраняются. Новые FTS: clinical_entry_search (резюме и JSON полей), import_search (полный источник истории), patient_search (код/обозначение, Unicode без учёта регистра). Триггеры поддерживают добавление; клинические записи/импорты по прежним правилам неизменяемы. Обозначение пациента синхронизируется при обновлении/удалении. Старый encounter_search остаётся.

Выборка ограничивается действующими связями врача на сервере до выдачи результата; фильтры не дают доступ к чужой карточке. GET параметры q/age_status/record_kind/route_category/attention сохраняются в URL. q — фраза из точных слов, без морфологии/семантического поиска; код дополнительно допускает буквальный подстрочный LIKE. Категория — наличие записи в истории, включая проекты, а не действующее назначение. pending — сохранённое критическое событие данного адресата/действующей связи без реакции, в том числе ещё не подготовленное worker. Нет сигнала ≠ нет риска. Не более 100 строк, порядок по коду; это не общий реестр всех пациентов организации.

Индексы: patients_age_code, relationship_doctor_patients, entry_patient_kind, proposal_patient_kind; прежний critical_events_patient используется повторно. search.json содержит EXPLAIN QUERY PLAN и 30 измерений каждой из 7 выборок на 6 синтетических пациентах; это малый локальный пример, не нагрузка S15.

## Доказательство расширяемости

extensions.py — отдельный, явно вызываемый модуль для НЕАКТИВНЫХ synthetic_test данных, не импортируется клиническим приложением. Он загружает декларативный JSON schema1 в прежние source_versions/catalog_versions атомарно, допускает только scale/drug/rule и test- namespace, повтор идентичной версии не дублирует, изменение той же версии отвергает. Исходные строки/версии не перезаписывает. Никаких eval/dynamic imports, clinical releases, автоматических назначений/алертов.

Две версии тестовой 42-пунктной шкалы с вымышленными текстами и вариантами 0–3 проходят прежний assessments.score_answers без изменения ядра. Ключ v1 даёт 42, v2 — 21 на ответах из единиц; старая версия повторно даёт 42, пропуск — None. Это проверка расширения ВНУТРИ поддержанного контракта 42/0–3, не новая медицинская шкала и не произвольная замена DASS. Две вымышленные карточки препарата читаются по version ID; два equals-правила в preview дают matched/no_match/unknown. Результат — только симуляция, без записи в critical_events/outbox. Реальная клиническая активация по-прежнему требует источника/популяции/прав/валидации/контрольных случаев и существующих ограничений продукта.

record_summary.py — отдельная новая функция: описательный подсчёт статусов четырёх полей из записей, без медицинского индекса. Проверена на одном синтетическом самоотчёте: records1/unknown4, остальные0. Это внутренняя read-only функция; публичного HTTP доступа к произвольному patient_id не добавлено.

Воспроизведение из корня: `.venv/bin/python -m evidence.S13.verify_extensions`. Результат extensions.json; test-bundle.json содержит все шесть версий. Новых версий нет в штатной базе/кабинете. db/assessments/clinical_rules/decisions/events/records и исходные ресурсы сохранены побайтно относительно начала S13. Добавление реального иного алгоритма/формата не объявляется «без изменения ядра» на основании этой узкой демонстрации.
