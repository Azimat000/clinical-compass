# BE15 — явное подтверждение синтетического плана

`plan-review-v1`. Только backend; активная база015 и интерфейс не переключены.
Клинический выпуск остаётся blocked. Все сценарии — вымышленные; техническое
подтверждение врача не заменяет независимую клиническую экспертизу BE19.

## Один механизм применения

Новый `backend_plan_reviews` хранит только происхождение неизменяемой редакции
`proposals`/`decision_drafts`. Отдельного действующего плана нет: прежние
`doctor_confirmations` → `care_actions` задают подтверждение и цепь замен.
`medications.approved/calendar/occurrences` читают явную замену состава из того
же payload; `adherence_tasks/entries` хранят пункты и результаты. Направление
записывается в прежний `referrals`, связанный с тем же действием. Старые
`therapy_courses`, подтверждения, отметки и исторические пункты не переписываются.

Миграция022 аддитивна и применяется только к отдельным синтетическим копиям.
Без неё новый API возвращает409; прежние ручные решения на схеме015 работают.
Откат разработки — исправляющий коммит. После применения022 не удалять историю
и не менять применённую миграцию: использовать следующую аддитивную миграцию.

## API

- `POST /api/v1/patients/{patient_id}/analyses/{run_id}/plan-reviews` — новая
  точная редакция; обязательный JSON и CSRF. Строгая схема `SCHEMA` в модуле.
  `analysis_revision/snapshot_id` указывают на готовый `plan`; `expected_version`
  и `parent_id` — на последнюю редакцию. `request_key` — случайные32hex.
- `GET /api/v1/patients/{patient_id}/plan-reviews/{proposal_id}` — квитанция,
  версия обычного proposal, содержание и состояние подтверждения. Только врач
  с текущей связью. История редакций остаётся в обычных решениях.
- `POST` по тому же адресу — отдельное `approved/rejected`, точная `version`
  из `proposal_version`, непустое `rationale`, `reviewed:true`. Другая версия409.
  Сохраняются прежние правила доступа/CSRF/no-store. Общий actions API закрыт.

В редакции врач выбирает неповторяющиеся `items:[{id,due_on}]` из точного
проверенного проекта и отдельно задаёт даты выполнения (или null). Обязательные
уточнения риска/диагноза удалить нельзя. Новые медицинские меры произвольным
текстом не добавляются. Собственные основание и неопределённости атрибутированы
врачу. Новая редакция создаёт новый proposal, не изменяет старый.

`medication:null` сохраняет уже действующий состав. Для замены нужен один
проверенный `recommendation_id`, точный структурированный `candidate`, явные
`start/days/times`. Альтернативы не превращаются в сочетание. Сила/единица/доза/
кратность/дробление/показание/фаза повторно проходят независимый v2. Дни и время
выбирает врач;366дней — технический предел формы, не клиническая рекомендация.
Поддержанные BE14 начало монотерапии и точное эффективное переносимое продолжение
сохраняются. Автоматических переходов/снижения/отмены не добавлено: BE14 для них
требует уточнения. Существующие отдельные ручные назначения/изменения/отмена
сохранены и проверены целевыми регрессионными тестами.

Для пункта `routing` нужна отдельная структурированная `routing`-оценка врача
(поля соответствуют существующему `routing.review`, без префикса `route_`).
Категория, срочность и взрослая применимость проверяются до черновика и снова
при подтверждении. При направлении лекарства сохраняются, если не выбрана
явная независимая допустимая замена; положительный риск не допускает обычную
лекарственную ветку. Новые сигналы BE09 остаются отдельным каналом врача.

## Проверка в одной транзакции

`decisions.confirm` — единственная точка записи подтверждения. Даже старый
прямой вызов выполняет `validate_confirmation`, затем прежний snapshot guard.
Внутри `BEGIN IMMEDIATE` повторно проверяются текущая роль/связь/синтетика,
последняя редакция, точный готовый анализ, источники и срок, диагноз, риски,
сверка лекарств, runtime и совпадение заново построенного payload.
Изменение входов/новая критическая запись/эпизод/отзыв источника дают отказ.
Проверка не вызывает модель внутри блокировки SQLite.

Подтверждение, одно действие, пункты, направление и аудит записываются атомарно.
Сбой записи/аудита откатывает всё. Конкурентные одинаковые подтверждения получают
одну квитанцию и одно действие; другой состав/версия получает409. Точный повтор
после новых данных возвращает уже записанное решение, не применяет план снова.
Отклонение допускается после устаревания, ничего не применяет. Пациентский
прежний API и календарь получают только утверждённое содержание.

Неподтверждённые BE15-редакции исключаются из клинического снимка `enrich`:
они не новые факты о пациенте и иначе сделали бы собственный диагноз устаревшим.
Они полностью сохранены в исходном журнале решений. Подтверждённое/отклонённое,
все прежние ручные проекты и реальные новые сведения входят в снимок как прежде.
После применения анализ закономерно устаревает: действие меняет клинический план.

## Доказательства

`apps/tests/test_backend_plan_review.py`: редакции, явное подтверждение, доступ,
свежесть/источники/риски, лекарственные отказы, откат, гонка двух соединений,
сохранность прежних отметок, существующий календарь и пункты/направления.
`evidence/BE15/http_protocol.py/json`: настоящий loopback HTTP, отдельный штатный
CLI-worker, один реальный запрос DeepSeek и полный путь до пациентской проекции.
Исходный диагноз в протоколе — явная структурированная механическая фикстура;
это не проверка качества диагноза настоящей моделью или медицинская валидация.
Общая регрессия отложена прямым поручением пользователя; целевые логи отдельно.
