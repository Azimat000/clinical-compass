# BE01: серверные контракты трёх результатов

Версия API 1.0, OpenAPI 3.1.0 в совместимом подмножестве JSON Schema; авторитетный файл — backend-api.json. Владелец — сервер HAC. Новый потребитель — будущий интерфейс врача. Существующие маршруты и формы не меняют свой договор. Закрытые перечисления/обязательные поля нельзя расширять без проверки потребителя: несовместимые изменения получают новый `/api/v2` и схему, старые записи остаются по исходной версии.

## Договор HTTP

`POST /api/v1/patients/{patient_id}/analyses` принимает только JSON `contract_version`, `operation` (ровно risk/diagnosis/plan), `request_key` (32 строчных hex). Требуются действующая сессия врача и `X-CSRF-Token`; пациент не может записать результат, источник, снимок, роль или clinical release. Возвращает 202 и Location даже при мгновенном age-отказе/повторе: запрос принят в журнал, `status` объясняет состояние. BE01 сохраняет очередь запросов; обработчик модели/диспетчер пока не подключён (BE04/06), поэтому queued не обещает фонового завершения сейчас. Публичной отправки результата/подтверждения нет.

Ключ повторения действует в пределах врач + пациент + request_key, хранится столько же, сколько неизменяемый запуск. Тот же ключ/операция возвращает текущую проекцию того же запуска; иная операция — 409. Новые сведения не заменяют снимок под старым ключом: возвращается stale, нужен новый ключ. BEGIN IMMEDIATE и UNIQUE исключают дубликат между процессами. Отдельный запуск каждой операции позволяет риску работать независимо.

`GET /api/v1/patients/{patient_id}/analyses/{run_id}` (также HEAD) — только действующему врачу той же связи, без изменения состояния. Чужой пациент/запуск — 404; пациентская роль — 403; без сессии — 401. Закончившаяся/заменённая связь не даёт доступа к старым анализам. Ответ `no-store`. Ошибки 400/401/403/404/405/409/413/415/500/503 имеют `{error,message}`; приватные тексты/SQL/стек в ответ и журнал не попадают. Повтор после 503 — с тем же ключом; после 409 сначала проверить сохранённый запуск/причину.

В снимок дополнительно входят SHA-256 точной схемы API и матрицы области: изменение договора/области также делает старый результат устаревшим.

Время — ISO 8601 с часовым поясом, сервер пишет UTC с микросекундами. ID непрозрачные строки. Неизвестные/повторные поля JSON, неверные типы и строки из одних пробелов отвергаются. `null` в result/model означает отсутствие результата/модели, не нулевой риск. Источники — идентификатор, точная версия, SHA-256 зависимостей снимка; цитирование внутри вывода отдельно привязывается к source_ids. Модель/версия/инструкция заполняются будущим исполнителем, сейчас null. BE01 не выдаёт свои синтетические примеры за генерацию настоящей модели.

## Состояния и неизменяемость

`queued → running → ready | insufficient_data | unsupported | failed | stale`; из queued допускаются также ранние insufficient_data/unsupported/failed/stale. Из готового/неполного/неподдерживаемого/сбойного результата — только stale. Нельзя повторно запустить терминальную запись: нужен новый запуск. Внутренний `advance` проверяет точный expected_revision; SQL дополнительно проверяет порядок/переходы и идентичность запуска. UPDATE/DELETE трёх новых таблиц запрещены.

- queued/running: результата ещё нет.
- ready: структурированный содержательный результат; это не доступность клинического выпуска.
- insufficient_data: нужны конкретные сведения; не отсутствие опасности.
- unsupported: контекст за пределами области; не отсутствие опасности.
- failed: техническая ошибка с кодом/признаком допустимости повтора; не отрицательный результат.
- stale: изменились входы/источники/дата, либо запись явно устарела. Предыдущий текст может оставаться для истории, использовать его нельзя.

GET вычисляет свежесть по повторному точному снимку и возвращает stale без перезаписи истории. `revision` обозначает сохранённую версию, `stale_reason` — отдельно вычисленное объяснение. BE06 добавит запуск/инвалидацию по событиям, это не обещание его готовности в BE01. Консервативное сравнение может признать анализ устаревшим даже от новой переписки; сейчас предпочтено повторное рассмотрение.

Клинический выпуск — независимое поле release. В этой версии допустимо только `blocked`/`be01-contract-only-v1`; клиент и внутренний исполнитель не могут включить клинику. Содержательные ready примеры проверяют контракт в синтетическом контуре, не доказывают клиническую точность. Старые B04/E02/E06, BE18/19 не сняты.

## Содержимое

Общее result: короткий summary, факты со ссылками `таблица:id` на сохранённые строки снимка (также `profile:patient_id`), противоречия, недостающие сведения, output. В BE02 добавлены точные ссылки `s2_…`, структурированные поля с исходным фрагментом и врачебное чтение замороженных источников; договор — [backend-snapshot.md](backend-snapshot.md). Старые ссылки сохранены для совместимости. Истинность извлечённого из свободного текста смысла ещё не проверяется: это BE05. Выводы требуют известных fact_ids/source_ids, уникальных ID; неизвестные ссылки отвергаются. Модельная память источником не считается.

RiskOutput содержит potential_risk с непустыми patterns либо явное no_pattern_found с пустым списком; последнее означает только «проверенные паттерны в анализе не найдены», не безопасность пациента. DiagnosisOutput содержит leading и alternatives. PlanOutput содержит diagnosis_run_id и непустые items; сервер требует актуальный ready диагноз этого же пациента/снимка. Это техническая привязка анализа, а не врачебно подтверждённый диагноз: BE11/15 добавят решение врача и связь полного плана. Ничего из этих объектов не применяется автоматически.

Примеры всех семи состояний и трёх форм результата — backend-api-examples.json. Сервер использует строгий проверяющий механизм ограниченного набора ключевых слов схемы; неизвестное ключевое слово схемы останавливает проверку. Это не универсальный валидатор OpenAPI, внешние ссылки запрещены. Примеры/HTTP/ошибки/реальная БД проверяются test_backend_contracts.py.

## Область и источниковые пределы

Машиночитаемая матрица backend-scope.json сохраняет три клинических результата и все F/M/E/T/C. Кандидаты V1 — взрослые с депрессивными/тревожными симптомами; будущие гипотезы F32/F33/F41.1 и существенные альтернативы, содержательный проект плана/лечения. Маниакальный/психотический/органический/связанный с веществами контекст, беременность/лактация и сложные сочетания требуют отдельной оценки области; не считать их автоматически отсутствующими. Это продуктовые ограничения автоматизации, не медицинское утверждение об исключении всех таких людей из помощи.

Официальные тексты 301_3/457_3 (2024) доступны и имеют взрослую популяцию; текущий статус применения отдельно не подтверждён. Отчёт evidence/BE01/research.md. Поэтому клинический выпуск заблокирован, проверка действующих оснований — BE03. Депрессивные/тревожные симптомы и балл анкеты не тождественны диагнозу.

BE01 исполняет только раннюю возрастную проверку по ages: неизвестность/противоречие/пограничный диапазон — insufficient_data, подтверждённый возраст младше 18 — unsupported, взрослый — queued (полная клиническая применимость ещё не определена). Возраст проверяется по датам и всем сохранённым источникам. Возраст каждого инструмента отдельный: PHQ9/GAD7 текущих выпусков 18–90; DASS текущая проектная граница 18–120 при неизвестном возрасте русской валидационной выборки. Правила анкет не меняются. Отсутствие/неприменимость анкеты не отменяет будущую оценку риска по другим входам.

## Численные технические бюджеты до оптимизации

Это цели и пределы ресурсов, **не уже достигнутые измерения** и не клинические сроки реакции:

| Измерение/ограничение | Бюджет |
|---|---|
| HTTP JSON body | 65 536 байт (существующий MAX_CONTENT_LENGTH) |
| Сохранённый входной снимок | ≤4 194 304 байт UTF-8; больше → 409 snapshot_too_large |
| Сохранённый ответ | ≤65 536 байт UTF-8; больше отвергается атомарно |
| Короткий вывод / отдельный факт | ≤600 / ≤2000 символов |
| Факты / выводы / источники | ≤100 / ≤100 / ≤500 |
| POST/GET без модели при 10 пациентах, 5 параллельных клиентах | p95 ≤500 мс, p99 ≤1000 мс, 0 потерянных/дублированных запусков |
| Будущий путь риска без модели | цель p95 ≤2 с от сохранённого события до outbox; не ждать диагноза |
| Будущая модель, диагноз / план | цель p95 ≤60 / ≤90 с; абсолютное ограничение задачи 120 с с явным failed |

Протокол BE17/18: до прогона зафиксировать commit, ОС/CPU/RAM, Python/SQLite/пакеты, размер базы/снимков, модель/точные инструкции/источники, холодный/прогретый режим. 20 прогревов, затем ≥200 POST/GET с уникальными ключами и отдельными повторами, 5 клиентов, монотонные часы; сохранять сырые времена, p50/p95/p99 ближайшим рангом, ошибки и дубли. Риск/диагноз/план измерять раздельно; качество на закрытом наборе — отдельно от скорости и от валидности JSON. Сейчас эти нагрузочные метрики не заявлены: BE01 проверяет договор и сохранность, не BE17/18.

## Миграция и восстановление

Миграция 016 добавляет только три таблицы/их индексы/триггеры. Проверка на приватной согласованной копии активной синтетической базы сравнивает все прежние строки/схемы/роли/историю и триггеры до/после, исключая одну новую запись schema_migrations; повтор migrate ничего не меняет. Рабочая база и работающие процессы в BE01 не обновляются. Развёртывание с новой схемой позднее — штатное создание резервной SQLite-копии и migrate. Откат: остановить использующий её процесс, вернуть согласованную предмиграционную копию с правами 0600 и прежний код; не удалять новые журналы вручную и не редактировать старые миграции. Новых зависимостей/внешних API/расходов нет.

входит в снимок; ready требует повторной проверки точной связи утверждения.
