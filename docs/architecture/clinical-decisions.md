# Ручные решения в синтетическом демо — S08A

Это дочерняя техническая часть исходного S08. Все пять действий (`therapy_start`, `therapy_change`, `therapy_stop`, `referral`, `plan_change`) вводит действующий связанный врач. Ни лекарственное правило, ни автоматическое назначение здесь не включены. Нет внешнего клинического утверждения или реального медицинского действия. S08/B04 и S09 остаются отдельными условиями.

Из карточки доступна страница `/patients/<patient_id>/decisions`. Врач видит справку с версиями/URL/разделами, создаёт проект с текстом/основанием/неопределённостью. Отдельная форма требует точную версию, обоснование подтверждения/отклонения и отметку просмотра. По умолчанию выбран отказ. Сохранение проекта не меняет план; отказ создаёт только неизменяемое подтверждение. Принятие создаёт `care_actions`, связанное составным внешним ключом только с `approved`. Сведения о лекарственном курсе автоматически не создаются: свободный текст не превращается в проверенную дозу или расписание приёма.

Новые `decision_drafts` связывают существующие proposals с автором, отношением врач–пациент, исходным проектом и полной версией справки. Номер версии монотонен внутри пациента, новая редакция — новый ID. Нельзя переписать проект/основания/подтверждение/действие. Журнал плана — цепочка всех подтверждённых решений пациента через `supersedes_id`; это предыдущая запись журнала, а не объявление об отмене конкретного лекарственного курса. Текст и вид каждого решения остаются отдельными. Для семантики лекарственных курсов нужны S08/S11.

В `BEGIN IMMEDIATE` повторно проверяются включённый аккаунт врача, текущая связь, доступ и synthetic=1. Проверка и создание действия выполняются одной транзакцией. Снимок охватывает профиль, визиты, наблюдения, самоотчёты, результаты анкет, НЯ, курсы, документы, сигналы, подтверждённые действия, источники/каталог/выпуск формы, ID связи, день Москвы и SHA версии справки. Любое отличие при принятии —409, даже если новая запись задним числом или содержит unknown. Это консервативная техническая защита, а не научный срок пригодности данных. Одновременные подтверждения сериализованы: первое меняет план, второе требует нового проекта. Истёкший проект допускается отклонить, но нельзя принять. Ни один свободный текст не интерпретируется как «противопоказаний нет».

Повтор сохранения связан с пользователем/пациентом/случайным ключом; другое содержание —409. Повтор идентичного уже записанного подтверждения возвращает его ID без нового действия; повтор с другим содержанием —409. При сбое аудита вся операция откатывается. Повтор подтверждения после новых данных — квитанция прежнего решения, не новое применение старого проекта.

Серверные роли/CSRF/изоляция действуют и на GET/API/POST. Пациентский список содержит только approved, без снимка входов/черновиков/отказов/справочного каталога; врач видит всё для своего пациента. HTML экранирует текст. Общий старый `/api/patients/<id>/actions` оставлен закрытым409, прямого обхода версии нет.

Справка `therapy-reference-v1.json` — краткое изложение листка ГРЛС с полным URL/хешем/разделами и указателями к двум КР. Это не полная инструкция и не исчерпывающая проверка противопоказаний/взаимодействий. `active_rules=false`, режим `reference_only`; изменение этого флага приводит к отказу модуля. Не созданы фиктивные reviewed_by или клинический выпуск. Ровно18/неизвестный возраст/неподходящее показание не запускают генерацию предложения: генератора терапии здесь вообще нет. Не выдавать это техническое отсутствие автогенерации за реализованный клинический оценщик.

Проверки: test_decisions.py, полный make check и реальный двухпроцессный smoke_restart.py с подтверждённым синтетическим изменением плана в обоих кабинетах. Отдельный тест конкурирующих подтверждений использует два SQLite-соединения. Проверки процесса не подтверждают клиническую применимость или безопасность лекарственного решения.
