# BE09: врачебный канал сигналов backend-alerts-v1

Владелец контракта — сервер HAC. Потребитель — уполномоченный ведущий врач
через будущий интерфейс или локальный HTTP-клиент с врачебной сессией.
Сигнал означает задачу рассмотрения синтетического эпизода BE08; клиническая
готовность всегда false. Доставка не устанавливает риск, диагноз или лечение.
Это не круглосуточная экстренная служба. Интерфейс уведомлений не возвращается.

## Происхождение и доставка

Четыре источника → backend.data_changed.v1 → BE06/BE07/BE08 → эпизод
risk-episodes-v1 → backend.risk_alert.v1 → существующий outbox worker →
существующая deliveries, channel=physician_api_v1 → врачебная HTTP-очередь.
Старый clinical.critical.medication_safety.v1 и его канал сохраняются отдельно.
Нового внешнего транспорта, webhook, email, стороннего адресата нет.

В режиме be08-context-v2 положительные правила BE07 и модельные предположения
порождают отдельные эпизоды/сигналы. Модельное предположение остаётся partial,
not_established, unreviewed. При missing_credentials правило доставляется без
ожидания диагностики/плана. Старый режим исполнения BE07 без эпизодов не
переводится на модель автоматически; для нового канала нужен явный opt-in BE08.

Публикация результата, эпизодов, backend_alerts и outbox проходит в одной
транзакции и общем savepoint; сбой откатывает всю публикацию. Один сигнал на
точную версию эпизода (UNIQUE episode_id,episode_revision). Повтор снимка не
создаёт новую версию. Новое основание того же открытого эпизода создаёт новую
версию и отдельный сигнал; старое рассмотрение не может закрыть новую версию.
При запуске worker существующие открытые эпизоды BE08 без сигнала догоняются
из журнала, без нового анализа/вызова модели. Закрытые эпизоды не поднимаются.

Транспорт — реальная долговечная локальная врачебная очередь в SQLite, доступная
через защищённый HTTP API. outbox-handler записывает deliveries и фиксирует
обработку одной транзакцией. Это именно помещение в канал; получение клиентом,
прочтение человеком и медицинское решение из этой записи не выводятся.
Повтор после сбоя/перезапуска идемпотентен. Два worker сериализуются SQLite.

В outbox payload только {"alert_id":"opaque-id"}. Клинические тексты находятся
в защищённой детали; attempts сохраняет только класс ошибки, без сообщения.
Backend alerts используют прежние outbox_attempts, deliveries и access.audit.
Связующая таблица и действия врача неизменяемы; старые журналы не переписываются.

## Адресат и сбой

Адресат закреплён исходной врачебной связью эпизода. Каждая доставка, выдача
очереди/деталей и действие повторно проверяют роль, disabled, начало/окончание
связи. Новый врач и новая связь прежнего врача не получают старый эпизод.
Автоматического переназначения/резервного доступа нет: отдельного оформленного
права в текущей модели данных нет. При отключённом/отсутствующем адресате
старый сигнал остаётся недоставленным в локальном операторском журнале.

Повтор доставки — прежний backoff min(2**attempt,60) секунд, максимум 5 попыток.
После пятой outbox=dead, API state=undelivered для сохранившего права врача.
Сигнал и все попытки остаются в базе; последующее включение адресата не
сбрасывает исчерпанный лимит автоматически. Новый операторский CLI:

```sh
.venv/bin/python -m apps.compass --db <synthetic-copy.sqlite3> backend-delivery-status
```

CLI локальный: непрозрачный ID/адресат/связь/статус/попытки/класс ошибки;
без текста, пациента, URL, пароля, модели. Старый delivery-status не меняет формат.
Внешний канал требует отдельного разрешённого канала и настройки прав.

## HTTP-договор

Cookie-сессия прежнего access; POST требует X-CSRF-Token. JSON UTF-8;
Cache-Control:no-store. Роль проверяется по базе. Анонимный запрос — 401,
пациент — 403, недоступный/несуществующий ID — 404. Чужой врач видит пустую
собственную коллекцию, деталей чужого сигнала нет.

| Метод/адрес | Вход и результат |
|---|---|
| GET/HEAD /api/v1/physician/alerts | Только page=1..999999; по умолчанию 1. 50 элементов, порядок queued_at,id по возрастанию; page,next_page(null в конце),items,version,clinical_ready. Дубли параметров/неизвестные параметры → 400. |
| GET/HEAD /api/v1/physician/alerts/{id} | Без параметров. Сигнал, текущая версия/история эпизода с основаниями и attempt_log. Без изменения отметок получения/просмотра. |
| POST /api/v1/physician/alerts/{id}/actions | Только application/json. Ровно action,expected_revision,reason,request_key. 200 и текущая деталь; 400 неверный JSON/поля, 415 media type, 409 конфликт/порядок/нет доставки. |

Все возвращаемые даты — серверные ISO8601 UTC с микросекундами. null означает,
что событие не зафиксировано, а не отсутствие клинического риска. ID непрозрачен.
Список не фиксирует снимок между страницами; при изменении доступа/новых записях
клиент перечитывает коллекцию и устраняет повторы по id. Фильтров/произвольной
сортировки/общего экспорта/публичного event-stream нет.

Сигнал: id,episode_id,episode_revision,created_at (время наблюдения версии),
queued_at,version,clinical_ready=false,channel,delivered_at|null,state,
queue{status,attempts,available_at,last_error},actions[]. Деталь добавляет
эпизод и attempt_log[{attempt,attempted_at,outcome,error|null}]. Последнее
действие не подменяет очередь доставки: оба поля сохраняются раздельно.
В детали эпизод может уже содержать новое основание; исходная версия сигнала
задана episode_revision и остаётся в его истории.

Последовательность state:

1. created_at: создано основание эпизода. queued_at: поставлен сигнал в outbox;
   при обычной публикации они фиксируются одной транзакцией, без промежуточного
   видимого клиенту состояния. При догоняющей доставке времена различаются.
2. queued: ждёт обработки; undelivered: попытки исчерпаны.
3. delivered: помещён в защищённый врачебный канал; GET/HEAD ничего не отмечает.
4. received: клиент врача явным POST подтвердил получение.
5. seen: врач явно отметил просмотр после received.
6. processed: врач с причиной завершил рассмотрение точной текущей версии
   эпизода после seen. Это не назначение и не подтверждение отсутствия риска.

Пример тела:

```json
{"action":"received","expected_revision":1,"reason":"","request_key":"receipt_example_0001"}
```

action закрытый enum received/seen/processed; revision — положительное целое
(не bool); reason — пустая строка для received/seen, непустая причина ≤1000
символов для processed. request_key — 16..80 ASCII букв/цифр/_/-, глобально
уникален в журнале действий. Точный повтор возвращает текущую деталь без нового
действия; тот же ключ с другим сигналом/версией/действием/причиной → 409.
Повтор действия с новым ключом тоже 409: клиент читает сохранённое действие.
Ключи сохраняются вместе с историей, сроки автоматического удаления не заданы.
Ошибка uses прежний JSON {error,message}, без стека/секретов.

processed атомарно закрывает эпизод с причиной, actor_id, request_key и точной
версией, затем добавляет action. Конкурирующее новое основание → 409, врач
перечитывает историю и обрабатывает новый сигнал. Транспорт и медицинские
care_actions/подтверждения/планы не меняются. Старые API/контракты/CLI сохранены;
новые маршруты и enum не добавляются в прежние строгие ответы анализов.

## Миграция и проверка

019_backend_alerts добавляет только связующий журнал/действия и их защиты.
Автоматически не меняет рабочую schema015, не включает backend_job_settings,
не обновляет сервис8000. До отдельного допуска запускать только в синтетической
копии после штатных migrate и явного synthetic opt-in. При восстановлении
сохранить историю/outbox; выключить worker/режим, вернуться к согласованной
резервной копии и прежнему коду, не удалять записи попыток/расходов.

Содержательные тесты — apps/tests/test_backend_alerts.py. Настоящие HTTP,
production worker без ключа, доставка правила и квитанция, затем перезапуск
сервера — evidence/BE09/live-channel.json. Получение подтверждает тестовый
авторизованный клиент врача; человеческое прочтение и клиническая проверка
этим не доказаны. Сохранность рабочей базы/80 таблиц/74 триггеров/доступов и
повторная миграция — evidence/BE09/copy-check.json. Общая регрессия — check.log.
Клинический выпуск blocked, BE18/BE19 и прежние блокеры обязательны.
