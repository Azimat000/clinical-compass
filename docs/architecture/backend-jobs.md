# Фоновые анализы — BE06

Только backend и синтетические данные, клинический выпуск blocked. Миграция
017 добавляет задачи, попытки, настройки и триггеры намерений к существующей
outbox. Рабочая база не мигрируется этим срезом. Новых пакетов нет.

## Активация и запуск

В отдельной синтетической базе после штатного migrate администратор явно задаёт
`UPDATE backend_job_settings SET enabled=1 WHERE id=1`. По умолчанию enabled=0:
прежний сервис и BE01-контракты продолжают работать без исполнения. Новые записи
после активации создают события; автоматического анализа старого архива нет.

Для независимости от долгой генерации нужны **два процесса**:

```
.venv/bin/python -m apps.compass --db var/isolated.sqlite3 worker --lane risk
.venv/bin/python -m apps.compass --db var/isolated.sqlite3 worker --lane generation
```

Первый обслуживает прежнюю outbox/критический транспорт и задачи risk; второй
только diagnosis/plan. `--lane all` сохраняет прежний однопроцессный запуск с
приоритетом риска между задачами, но не прерывает уже выполняющуюся генерацию.
`--once` обрабатывает доступную работу до опустошения; будущие повторы ждут
постоянного worker. В режиме без новых таблиц импорт безопасен (schema015).

Исполнителей трёх клинических операций ещё нет: они относятся к BE07/10/12.
Настоящий штатный исполнитель BE06 возвращает `operation_unavailable`; после
трёх попыток результат failed, result=null, а не «риска нет». Модель не
подменяется имитацией успешного медицинского ответа. Для последующей реализации
есть внутренний `executor(operation, frozen_snapshot)`; он возвращает status
ready/insufficient_data/unsupported, result/errors/model. Публикация проходит
прежнюю проверку контракта, ссылок, источников, возраста и точной диагностики
плана. Этот интерфейс не доступен пользователю по HTTP.

## Атомарность и повторяемость

Триггеры clinical_entries, first_visit_versions, observations (insert/update),
assessment_results создают `backend.data_changed.v1` в той же транзакции, что
новые сведения/исправления. Это четыре исходных вида данных; отдельные строки
наблюдений покрывают анамнез. Откат сохранения откатывает намерение. Несколько
событий одной записи допустимы: потребитель сводит их к одному текущему снимку
по 128-битному ключу SHA256(auto-risk:canonical_snapshot)[:32], в области
actor+patient. Старое событие после смены связи не переадресуется новому врачу.

Сохранение записи не вызывает модель, не строит большой снимок и не ждёт её.
Прежние evaluate_safety/критические события остаются в транзакции сохранения.
Большие истории читаются через принятый полный BE02 snapshot: без молчаливой
обрезки, предел 4 МиБ сохранён. Не удалось собрать снимок — событие повторяется
существующей outbox до пяти попыток, затем dead с типом технической ошибки.
Ни failed, ни dead не свидетельствуют об отсутствии риска. Деление текста для
смыслового анализа будет частью конкретных исполнителей; BE06 не делает
неподтверждённых выводов и не обходит лимит BE05.

Явные POST /api/v1/patients/{id}/analyses создают diagnosis/plan/risk. Только
врач с текущей связью. Запуск, снимок, первая версия и задача пишутся одной
транзакцией. Повтор request_key возвращает прежний запуск, не создаёт дубль.
При age_scope-отказе сохраняется конечное состояние без фоновой задачи.

## Исполнение, сбои и отмена

BEGIN IMMEDIATE удерживается только при коротком claim/finish. Генератор/сеть
выполняется вне транзакции. Задачи risk выбираются раньше generation; outbox
сначала обслуживает прежний clinical.critical, затем намерения backend, затем
обычные события. Один процесс может владеть задачей: случайный token, lease
90 секунд (дольше максимальных 60 секунд адаптера BE04). Потерянный worker
восстанавливается после истечения lease. Любое позднее завершение со старым
токеном либо после окончания lease отвергается. Публикация и завершение задачи
атомарны; UNIQUE(run_id, revision) и переходы схемы016 сохраняются.

Максимум три попытки, задержки 2/4 секунды перед повторами. Исчерпанный lease
также считается попыткой. История backend_job_attempts сохраняет start/end,
expired/retry/done/failed/stale/cancelled. Во время повтора публичный статус
running (результата нет); подробный технический статус — в серверной таблице.
Ошибки исполнителя сводятся к фиксированным кодам; чужие exception messages,
медицинский текст, ответы поставщика и ключи не логируются.

Внутренняя `backend_jobs.cancel(db, user, patient_id, run_id)` повторно проверяет
доступ и обнуляет token: публичный failed/errors.cancelled, очередь cancelled.
Повтор отмены безопасен. Уже конечный результат не переписывается. Принудительно
остановить уже отправленный внешний HTTPS отмена не обещает; поздний ответ
записать нельзя, бюджетная резервация BE04 не сбрасывается. HTTP/UI отмены здесь
не добавляются.

## Свежесть и доступ

Снимок при включении содержит backend_runtime: версию задач/генератора,
точный model ID, версию адаптера, SHA256 системной инструкции и версию извлечения.
При изменении реализации исполнитель обязан менять generation_version.
Источники со сроками/отзывом и все данные остаются в прежнем хеше снимка.

Перед claim, перед finish под блокировкой записи и при каждом чтении снова
проверяются роль/disabled, точная care_relationship, данные/дата/источники и
runtime. Старые данные или непроверяемая свежесть → stale; результат не текущий.
Отзыв доступа не позволяет получить исходный снимок/результат; старый врач и
новая связь того же врача не наследуют предыдущий запуск. Во время работы
права проверяются по базе, а не по переданному объекту user. Выключение
настройки также запрещает публикацию и делает прежние результаты устаревшими.

## Проверка и восстановление

apps/tests/test_backend_jobs.py покрывает rollback, четыре источника,
исправления, coalescing, запросы врача, две связи SQLite, leases/fencing,
повторы/сбои, отмену, доступ/смену врача, свежесть данных/модели/источника,
проверку результата, отсутствие блокировки на время исполнителя и прежний
критический приоритет. Технический executor в тестах явно искусственный и не
проверяет качество медицины.

`PYTHONPATH=. .venv/bin/python evidence/BE06/live_process_check.py` запускает
два реальных процесса одновременно на новой синтетической базе, убивает
владельца generation, ждёт настоящие 90 секунд аренды и перезапускает штатный
worker. Риск завершается технической ошибкой ещё при живом долгом generation;
восстановление/предел попыток/ровно одна конечная версия сверяются в SQLite.
Внешних вызовов нет: проверяется настоящий отказ отсутствующего исполнителя,
не недоступность сети DeepSeek и не качество клинических функций.

Откат: остановить workers, enabled=0; не удалять attempts/снимки и не править
старые миграции. Для проверочной копии допустима новая копия до017; рабочая
база/учётные записи/8000 не изменены и не требуют восстановления.
