# Решение врача по гипотезе — diagnosis-review-v1

BE11, только сервер и синтетические случаи. Клинический выпуск заблокирован.
Это отдельный журнал решения врача; исходный результат модели остаётся
`unreviewed`, а лекарства, направления и подтверждённый план не изменяются.

## HTTP и точные поля

`GET /api/v1/patients/{patient_id}/diagnosis-review?page=1` возвращает
`head_version`, текущий `snapshot_id`, `current` и историю по 50 записей
(`page`, `page_count`). Только текущий уполномоченный врач; Cache-Control:no-store.
Строгий JSON запроса реализован в `backend_diagnosis_review.SCHEMA`;
неизвестные/повторные поля и параметры адреса отклоняются.

`POST` на тот же адрес требует Content-Type:application/json и X-CSRF-Token.
Все следующие поля обязательны, nullable поля передаются явно:

| Поле | Значение |
|---|---|
| request_key | 32 строчные шестнадцатеричные цифры, новый для нового решения |
| expected_version | head_version, целое >=0; 0 до первого решения |
| snapshot_id | точный SHA256 текущего снимка, 64 шестнадцатеричных цифры |
| action | accept / modify / reject / manual |
| run_id | ID анализа для первых трёх действий, null для manual |
| analysis_revision | точная версия ready-анализа, null для manual |
| hypothesis_id | ID ведущего или альтернативного предложения, null для manual |
| diagnosis | текст врача для modify/manual (до2000), иначе null |
| diagnosis_code | собственный код врача (до64) или null; при accept/reject только null |
| basis | непустое основание, до4000 |
| uncertainties | непустое описание неопределённости, до4000 |
| reviewed | только true, отдельное подтверждение просмотра |

`accept` копирует выбранный текст предложения дословно и сохраняет его
отдельно как `model_suggestion`; происхождение диагноза `physician_acceptance`.
Текст может содержать исходную оговорку модели; статус врача хранится отдельным
полем, а исходник никогда не переименовывается в подтверждённый машинный диагноз.
`modify` сохраняет собственный текст/код врача и точное исходное предложение;
`manual` сохраняет собственный текст/код без притворной связи с моделью.
Собственный код является непрозрачным текстом врача, автоматической проверки
классификатора/выбора кода здесь нет. Происхождение собственного текста —
`physician_authored`; статус записи — `physician_recorded`.

`reject` сохраняет отказ и основание с точным предложением, диагноз=null.
Каждое новое действие явно заменяет предыдущую текущую версию. После отказа
действующего подтверждённого диагноза нет; прежний текст остаётся в истории.
Если врач хочет сохранить прежний диагноз при новом рассмотрении, он делает
новую собственную запись. Ничего не удаляется незаметно.

Успех200 — неизменяемая квитанция с id/version/previous_id, автором, связью,
временем, основанием/неопределённостью, снимком, точными source refs,
run_id/analysis_revision/hypothesis_id, model_suggestion/model_context,
диагнозом и происхождением. `clinical_ready=false`, `clinical_release=blocked`,
`treatment_applied=false`. Повтор возвращает ту же историческую квитанцию;
её получение не означает, что она всё ещё текущая — для этого нужен GET.

## Свежесть, история и гонки

Перед новой записью сервер повторно проверяет роль/disabled/текущую связь,
синтетический случай, непротиворечивый возраст18+, полную версию сведений и
источников, актуальный ready-диагностический анализ и хеш механизма анализа.
Чужое/устаревшее/незавершённое предложение не принимается. Источник нельзя
подменить полем запроса. Отрицательный/неполный ответ не превращается в диагноз.

BEGIN IMMEDIATE и UNIQUE(patient_id,version) сериализуют два соединения.
expected_version фиксирует предыдущую вершину. Два различных решения с одной
базовой версией дают один успех и один409. Одинаковые ключ/содержимое дают
одну запись и одинаковую квитанцию, включая после перезапуска/новых данных/
нового решения; изменённое содержимое с прежним ключом даёт409. Перед повтором
всё равно проверяется текущая связь; прежняя связь не даёт повторно использовать
квитанцию. UPDATE/DELETE запрещены триггерами; версия и previous_id проверяются
на сервере и в SQLite. Аудит и запись атомарны.

Снимок решения врача хранится в analysis_input_snapshots; исходный model run
и его неизменяемые версии остаются отдельно. История доступна текущей связи;
для прежней связи не выдаются квитанции из этого API. Глобальная head_version
сохраняется для предотвращения конкурирующих решений между сменами связи.

В decisions.snapshot добавлен diagnosis_review: версия и авторское решение
с источниковым снимком. Если записей нет или рабочая схема015 не содержит
таблицы, прежний формат снимка сохраняется. Любое новое решение делает
прежние анализы и проекты плана устаревшими; существующее серверное confirm
отказывает в применении такого проекта. Ранее подтверждённое лечение не отменяется.
Новые существенные данные/источники/дата/связь также меняют снимок.

GET показывает свежесть текущего диагноза, сравнивая сохранённый снимок с
текущим без самого diagnosis_review: собственная запись не делает собственное
основание устаревшим. Если данные изменились, current.diagnosis=null,
current.fresh=false, историческая квитанция остаётся дословной.
При недоступности источников история остаётся доступной, snapshot_id=null,
freshness_error объясняет невозможность нового решения. Свежесть не означает
независимую клиническую валидацию. BE12 обязан проверять fresh и отдельный допуск
будущего плана, а не читать исторический диагноз как безусловно действующий.

## Хранение и выпуск

Миграция020 только добавляет backend_diagnosis_reviews и защитные триггеры.
Таблица ссылается на автора/связь/снимок и точную версию модельного анализа.
Проверки выполняются во временных синтетических SQLite и на копии рабочей базы;
рабочие8000/worker/схема015 не обновляются в этом срезе. Нет новых зависимостей,
медицинских порогов, передачи данных поставщику, платных вызовов или смены модели.
После отдельного будущего решения о миграции запуск приложения применит020;
пока интерфейс этого API не вызывает. Для восстановления рабочая база не требует
отката; проверочные копии можно удалить. В базе с записями нельзя удалять миграцию
или сбрасывать историю; нужен обычный новый исправляющий коммит/миграция.

Проверки: test_backend_diagnosis_review.py; evidence/BE11/verify.py
(реальный локальный HTTP, повтор после перезапуска, миграция копии, сохранность).
Это технические проверки авторской синтетики с явной тестовой моделью,
а не доказательство диагностического качества или клинической безопасности.
