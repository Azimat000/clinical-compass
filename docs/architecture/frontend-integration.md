## Обнаружение последнего анализа и история

Добавлено `GET/HEAD /api/v1/patients/{patient_id}/analyses`.
Это дополнение чтения к прежнему POST того же адреса, не новая очередь/журнал.
Данные берутся из analysis_runs/result_versions через прежний analyses.read;
разрешение — текущая связь врача с синтетическим пациентом. Старая связь даже
того же врача не открывает прежние анализы. Никакого автоматического создания.

Параметры: `operation` необязателен, только risk/diagnosis/plan; `page` целое
1–1000000, по умолчанию1. Повтор любого параметра/неизвестный параметр/пустой
operation/несуществующая страница →400. Без записей доступна страница1.
Постоянный размер страницы10. Сортировка created_at DESC, id DESC.

Ответ200/no-store:

```json
{
  "contract_version": "1.0",
  "patient_id": "P201",
  "operation": "diagnosis",
  "page": 1,
  "page_size": 10,
  "page_count": 1,
  "total": 0,
  "backend": {"enabled": false, "generation_version": null},
  "items": []
}
```

items содержит полные прежние объекты Analysis; тот же schema validator,
ограничения/источники/result/errors/model/revision/snapshot_id/stale_reason.
Последний запуск: items[0] на page1 с operation. Он может быть failed/stale/
insufficient_data; нельзя пропускать его ради более старого ready. В одном
SQLite read snapshot выполняются count/выбор/read, свежесть пересчитывается
без записи версии. Страницы между отдельными запросами могут сдвигаться при
появлении нового запуска; клиент обновляет первую страницу и убирает дубли по
run_id. Внутри ответа порядок согласован. Пустой список не означает «риска нет».

backend.enabled — настройка разрешения очереди, а не heartbeat процесса и не
доказательство исправной модели. Старые данные остаются историей после
выключения. Диагноз/план по-прежнему запускаются явным POST; автоматическая
координация новых сведений делается FE06/FE07, не браузерным чтением.

Прежний контракт backend-api.json не переписывался: его хеш закреплён в
клинических снимках/quality gate. Новый интерфейс чтения описан здесь; Analysis
и CreateAnalysis остаются прежними. Клинические runtime gate совпали с BE16.

## Фактические операции для трёх блоков

Все адреса ниже начинаются с `/api/v1`, только текущая роль doctor. Врач
авторизуется серверной cookie; каждая запись требует X-CSRF-Token. Анонимная
или истёкшая сессия401, пациент403, чужой пациент404. Чтения no-store.

| Назначение | Адрес после /api/v1 | Содержание |
|---|---|---|
| Главная: сигналы | GET physician/alerts?page=1 | inbox текущего врача, история действий, доставка |
| Основания сигнала | GET physician/alerts/{id} | эпизод, точные версии, источник; не просто счётчик |
| Действие с сигналом | POST physician/alerts/{id}/actions | прежний серверный журнал; собственное подтверждение врача |
| Последний/история | GET patients/{p}/analyses?operation=risk/diagnosis/plan&page=1 | существующие запуски, состояние/свежесть |
| Явный запуск | POST patients/{p}/analyses | contract_version1.0, operation, request_key;202+Location |
| Состояние запуска | GET patients/{p}/analyses/{run} | Analysis, версия и результат/конкретные ошибки |
| Подробности гипотезы | GET patients/{p}/analyses/{run}/diagnosis-context | гипотезы, критерии/нехватка/цитаты; до готовности409 |
| Подробности риска | GET patients/{p}/analyses/{run}/risk-context | смысловая оценка и история; до наличия409 |
| Исходные данные | GET patients/{p}/analyses/{run}/inputs?page=1 | версия, полнота, записи, страницы |
| Точная исходная версия | GET patients/{p}/analyses/{run}/inputs/{reference} | source_ref из снимка, не произвольный внешний URL |
| Отмена | POST patients/{p}/analyses/{run}/cancel | пустой JSON, прежняя очередь/защита от старого процесса |
| Диагноз врача | GET/POST patients/{p}/diagnosis-review | current/history/fresh; запись action accept/edit/reject, версия, причина |
| Сверка терапии | GET/POST patients/{p}/therapy-context | отдельные кодированные данные врача; неизвестное не отрицается |
| Проект врача | POST patients/{p}/analyses/{run}/plan-reviews | редактирование из точной текущей версии системного проекта |
| Квитанция/подтверждение | GET/POST patients/{p}/plan-reviews/{proposal} | чтение отдельно; POST явное подтверждение с версиями |

Точные строгие тела записей не дублируются вторым контрактом: их проверяют
backend_diagnosis_review.record, backend_therapy_context.SCHEMA,
backend_plan_review.create/confirm и действующие тесты/документы BE11/14/15.
Формы FE06–FE08 должны собирать именно эти поля, не подставлять actor/release.
План пациента остаётся на прежнем `/api/patients/{p}/decisions` и календаре:
там только отдельно утверждённые действия. FE02 не подтверждает план/диагноз.

## Наблюдённые состояния и частота чтения

Настоящий Waitress + две штатные CLI-очереди/обычный executor, одна копия P201:
risk insufficient_data0.642s (нет структурированного текущего контекста врача),
plan insufficient_data0.709s (нет актуального разбора/диагноза),
diagnosis failed6.914s (три bounded попытки, внешний код executor_error).
Это один технический прогон, не SLA или измерение качества медицины.
Офлайн проверка точного диагностического снимка:62166/63532байт при16000,
причина context_limit; расчёт резервов70358/71724microUSD также выше20000.
Настоящий ключ был передан только двум worker; сетевых модельных вызовов0.
Нельзя выдавать эти ошибки за содержательный ответ модели/готовую демонстрацию.

Для FE05–FE07 исходная настройка опроса: только queued/running,1s первые5с,
затем2s до10s; после10s прекратить автоматический опрос и оставить ручное
«Проверить состояние». Останавливать на terminal, скрытой вкладке, потере
сессии/доступа или уходе со страницы. Один запрос в полёте, никаких автоматических
POST при опросе/повторе GET. Новый результат не трогает ввод/фокус врача.
Это предлагаемые границы клиента на основании данного прогона, реализация и
дальнейшая проверка в FE05–FE07. Положительные примеры/подготовка данных — FE03;
ограничение размера не снимается обрезанием или стиранием исходной истории.
