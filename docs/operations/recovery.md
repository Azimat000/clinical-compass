# Копии и восстановление локального синтетического прототипа

Режим: SQLite DELETE/FULL на локальном диске, один сервер Waitress и worker, без внешнего медицинского запуска. Копия содержит исходные тексты, сообщения, индексы, пароли в виде хешей, сессии и токены защиты: это такой же закрытый файл, как исходная база. Не помещать его в static/Git/публичное облако и не передавать без отдельного основания. Шифрование/защита от владельца машины этим механизмом не обеспечиваются.

## Создать и проверить копию

Из корня проекта, под тем же локальным владельцем, отдельный **новый** путь:

```sh
umask 077
.venv/bin/python -m apps.compass.backup backup var/compass.sqlite3 var/backups/NEW-snapshot.sqlite3 > var/backups/NEW-snapshot.json
```

Каталог `var/backups` создать заранее с правами 0700 (`mkdir -m 700 -p var/backups`) до перенаправления `>`; NEW заменить новым уникальным именем. Команда читает существующий источник через mode=ro, применяет SQLite online backup, проверяет целостность и внешние ключи источника/результата. Файл назначения создаётся исключительно новым с правами 0600, затем синхронизируется с диском вместе с каталогом. Существующие файлы/символические ссылки назначения не перезаписываются. Код завершения должен быть 0; JSON должен содержать sha256, completed_at, integrity_check=ok и пустой foreign_key_check. Не считать существование файла доказательством успешной копии. Сохранить JSON отдельно от базы; хеш выявляет изменение, но не является подписью и не защищает от подмены обоих файлов.

Online backup допускает работающий сервер; при длительных конкурентных записях операция может ждать/перезапускать страницы. Точную точку снимка между началом и завершением без дополнительного контроля не обещать. Простое `cp` живого SQLite-файла не использовать. Нельзя удалять `-journal`, `-wal` или `-shm` у аварийной базы.

## Восстановить

1. Остановить сервер, worker и резервную консоль. Убедиться, что процессов с этой базой нет. Сохранить аварийный комплект файлов отдельно с прежними правами; не исправлять его на месте. Зафиксировать момент отказа, последнюю проверенную копию и перечень подтверждённых/неподтверждённых отправок.
2. Восстановить **в новый путь**, подставив SHA из сохранённого JSON:

```sh
.venv/bin/python -m apps.compass.backup restore var/backups/NEW-snapshot.sqlite3 var/RESTORED.sqlite3 --sha256 SHA_ИЗ_JSON
.venv/bin/python -m apps.compass --db var/RESTORED.sqlite3 migrate
.venv/bin/python -m apps.compass --db var/RESTORED.sqlite3 status
```

3. Сверить миграции, ожидаемые записи, критические события/адресатов/квитанции и время снимка. SHA проверяется до копирования; миграции штатной командой сверяются с закреплёнными SQL. При ошибке не запускать и не удалять исходные файлы. Для аварийного отката не применять новый код со старой схемой без проверки совместимости.
4. Запустить сервер и worker с явным `--db var/RESTORED.sqlite3` (перед подкомандой). Переподключить местную резервную консоль к **тому же пути**. Проверить вход двух ролей, чтение существующего самоотчёта, новую контрольную отправку, статус очереди и доступность критического сигнала. Не подтверждать просмотр/реакцию врача автоматически. Все старые учётные данные/сессии восстановлены из снимка; для компрометации секретов нужен отдельный отзыв, обычный restore этого не решает.
5. Учесть все записи после точки копии: их нет в восстановленной базе. Повторять сохранённую форму с тем же ключом лишь после сверки результата; повтор одинаковой операции не должен давать дубль. Ключи/тексты не журналировать. Восстановленная до отправки база не знает позднего ключа: повтор создаёт утраченную запись заново, не восстанавливает её старое время/квитанции. При отсутствии сохранённой формы/другого источника поздние данные невосстановимы. Не выдавать пропавший сигнал за отсутствие риска.

## Измеренные пределы и эксплуатация

Опыт S15: настоящий SIGKILL сервера и worker внутри незавершённой транзакции; разрыв TCP до приёма и после сохранения; повреждение заголовка остановленной базы и реальный restore; отдельный hot journal с вытесненными грязными страницами. Числа и метод: evidence/S15/recovery.json и recovery.md. Все строки всех 77 таблиц снимка сравнивались до новой контрольной записи. Потеря питания/машины/диска не проверялась. Хост, сервер, копия и клиент на одном ноутбуке; это не независимая аварийная площадка.

Автоматическое расписание копий, их независимое хранение, шифрование, срок хранения, дежурство и внешний мониторинг ещё не внедрены. Перед/после каждой локальной демонстрации сделать новую проверенную копию и периодически выполнять пробное восстановление. Это ручная процедура, а не гарантированный интервал: возможная потеря охватывает всё после последней годной копии, в том числе критические события и квитанции. Если копия единственная и на том же диске, отказ диска может уничтожить всё. RTO опыта исключает ожидание человека, обнаружение инцидента и загрузку из удалённого хранилища. B16/клинические/правовые ограничения остаются до внешнего режима.


## Уточнение снимка — 20.10.2026, техническое исправление

JSON копирования/восстановления теперь содержит snapshot_rows: число строк каждой таблицы фактически созданного снимка. Оно вычисляется по копии, а не по меняющемуся источнику. recovery_limit прямо напоминает: более поздних записей/сигналов/квитанций в старой копии нет. Сверяйте эти количества с сохранённым описанием копии; совпадение количества не доказывает идентичность содержания, её проверяют SHA и сопоставление строк в испытании. Файлы JSON по-прежнему приватные.

Это средство сверки, не непрерывное резервирование и не устранение потери после точки снимка. Независимый диск/аварийная площадка, согласованный интервал потери, шифрование, дежурство и фактический внешний канал не появляются из нового поля. Восстановление требует отдельной сверки поздних отправок; отсутствие сигнала в восстановленной базе не подтверждает отсутствие риска.
